# SQL Agent Evaluation Report

## Architecture

```text
User question
    -> Agent loop (local Ollama JSON decision)
    -> SQL generation tool (schema-aware SELECT or unsupported response)
    -> Read-only SQLite executor
    -> Rows or SQL error
    -> Agent loop asks Ollama for a grounded final answer
    -> User answer + evaluation/conversation log
```

The database contains `customers`, `products`, `orders`, and `order_items`.
The executor accepts only one read-only `SELECT` or `WITH` statement and limits
the number of returned rows.

## Results

The evaluation contains 17 questions with 3 trials per question:

| Metric | Result |
|---|---:|
| pass@1 (first trial status was `ok`) | 11/17 (64.7%) |
| pass^3 (all three trials status `ok`) | 10/17 (58.8%) |

These metrics measure the recorded `status` field. They do not guarantee that
every `ok` answer is numerically correct; for example, one recorded answer
reported 0% cancelled orders even though the expected result was 25.0%.

## Three common failure types

1. **Schema/unsupported-question misclassification**  
   The model marked a valid spending question as unsupported because it looked
   for a `sales` or `transactions` table. Example: *“How much did customer 1
   spend in January 2025?”* was rejected even though spending can be derived
   from `orders` and `order_items`.

2. **Invalid SQL generated by the small model**  
   Example: the month-over-month revenue query generated
   `SUM oi.quantity * oi.unit_price`, which is invalid SQLite syntax. The
   executor returned a syntax error.

3. **Local model timeout**  
   Example: one trial of the month-over-month revenue question failed with
   `Ollama request failed: timed out`. This depends on local model response time,
   not the database.

## Improvement

The agent was changed to include the exact executor error and the complete
schema in the next SQL-generation prompt. Failed SQL can now be corrected and
retried within a six-step cap instead of ending immediately.

| Measurement | Before | After |
|---|---:|---:|
| SQL correction retries after an executor error | 0 | Up to 5 |
| Maximum agent steps | 1 failure-ending path | 6 |

The repository contains the after-run results above, but not a baseline log from
the earlier revision, so a before/after pass-count comparison cannot be verified
from the available artifacts.
